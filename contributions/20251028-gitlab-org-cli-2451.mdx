# Contribution Summary

## What was done

This contribution significantly expands the `glab` CLI's project management capabilities by introducing a new `repo members` subcommand. Specifically, two core commands were added: `glab repo members add` and `glab repo members remove`.

The `glab repo members add` command allows users to invite or add existing users to a project. This command supports identifying users either by their username or their numerical user ID. It provides comprehensive options for defining the member's access level, mapping directly to GitLab's standard permission levels: Guest (10), Reporter (20), Developer (30), Maintainer (40), and Owner (50). Additionally, users can specify an optional expiration date for the membership, after which the user will automatically be removed from the project.

The `glab repo members remove` command enables the removal of existing members from a project. Similar to the `add` command, it supports identifying the target member by either their username or user ID, ensuring flexibility in administrative operations.

The implementation involves creating new command structures within the `repo` context, handling input parsing for user identifiers, access levels, and dates, and interfacing with the GitLab API's project members endpoints for both adding (`POST /projects/:id/members`) and removing (`DELETE /projects/:id/members/:user_id`) members.

## Impact

These changes introduce a crucial set of new capabilities for `glab` users, particularly project maintainers and administrators. The primary impact is enabling direct command-line management of project memberships, which was previously unavailable. This enhances the CLI's utility for automating administrative tasks, scripting onboarding/offboarding processes, and managing user access in a programmatic way.

*   **New Capabilities**: Users can now add and remove project members directly from the command line, offering granular control over project access.
*   **Improved Functionality**: Streamlines project administration by providing a consistent and scriptable interface for member management, reducing reliance on the web UI for these common tasks.
*   **Automation**: Facilitates the creation of automation scripts for user provisioning and de-provisioning within GitLab projects, leading to increased operational efficiency.
*   **Scope**: This impacts all `glab` users who interact with GitLab projects and require administrative capabilities, particularly those managing teams and access levels. There are no breaking changes introduced, as this is purely an additive feature.

## Technical details

The implementation primarily involves creating new Go files under the `cmd/repo/members` directory (e.g., `cmd/repo/members/add.go` and `cmd/repo/members/remove.go`) to define the new subcommands and their flags.

*   **Command Structure**: The commands follow the standard Cobra CLI framework pattern, nested under `glab repo members`. Flags are defined for `--user`, `--user-id`, `--access-level`, and `--expires-at`.
*   **API Interaction**: The commands utilize the existing GitLab API client within `glab` to make authenticated HTTP requests to the respective `/projects/:id/members` endpoints.
    *   For adding members, a `POST` request is made, including `user_id`, `access_level`, and optionally `expires_at`.
    *   For removing members, a `DELETE` request is made to `/projects/:id/members/:user_id`.
*   **Data Parsing and Validation**: Input for access levels is mapped from user-friendly string names (e.g., "developer") to their corresponding numeric GitLab access level IDs (e.g., 30). Date parsing is implemented for the `expires-at` flag. Robust input validation is performed to handle invalid user identifiers, non-existent users, or incorrect access levels, providing clear error messages.
*   **Testing**: The functionality is thoroughly covered by extensive unit tests. These tests utilize HTTP mocking to simulate GitLab API responses for various scenarios, including successful operations, user not found errors, permission denied errors, and invalid input cases. This approach ensures the reliability and correctness of the API interactions without requiring live GitLab instances.
