# Contribution Summary

## What was done

- Implemented a robust API documentation generation workflow for Brainglobe projects using Sphinx and its `autodoc` extension. This addresses the long-standing need for comprehensive API references.
- A new Python script was introduced to dynamically fetch external Brainglobe repositories (e.g., `brainglobe-atlasapi`) from GitHub. This makes their source code available locally for Sphinx to parse, enabling a centralized documentation portal for distributed projects.
- The main Sphinx configuration file (`conf.py`) was significantly updated to integrate new extensions like `autodoc`, `napoleon` (for Google/NumPy style docstring support), and `intersphinx`.
- Documentation paths within the Sphinx build environment were adjusted to correctly locate the source code of the newly fetched external repositories.
- Dedicated API documentation pages (e.g., within an `api/` directory) were created for specific modules like `brainglobe-atlasapi`, automatically extracting and rendering their docstrings into `reStructuredText` (`.rst`) format.
- The documentation build workflow was enhanced to include necessary Python package installations (e.g., `sphinx`, `sphinx-rtd-theme`, `numpydoc`) and clear setup instructions, ensuring reproducibility and ease of deployment.

## Impact

- **Enhanced Developer Experience**: Provides comprehensive, up-to-date, and automatically generated API documentation directly from source code, making it significantly easier for developers to understand and contribute to Brainglobe libraries, starting with `brainglobe-atlasapi`.
- **Improved Maintainability and Consistency**: Automating documentation generation reduces manual effort, minimizes the risk of documentation becoming outdated, and ensures consistency between code and its API reference.
- **Unified Documentation Portal**: Establishes a foundational framework for easily integrating API documentation from other existing and future Brainglobe repositories into the main `brainglobe.github.io` website, fostering a unified and accessible documentation hub.
- **New Capability**: The project now possesses a powerful mechanism for dynamically pulling in and documenting external codebases, crucial for an ecosystem composed of multiple independent libraries.

## Technical details

- **Modified Files and Components**:
    - `conf.py`: Extensive modifications including:
        - Updates to `sys.path` to include paths to fetched external repositories.
        - Addition of `sphinx.ext.autodoc`, `sphinx.ext.napoleon`, `sphinx.ext.intersphinx`, and other relevant extensions to the `extensions` list.
        - Configuration of `autodoc_member_order = 'bysource'` to maintain logical order.
        - Potentially, `html_theme` and other theme-related options were configured.
    - New `.rst` files (e.g., `api/brainglobe_atlasapi.rst`): Created to house `.. automodule:: brainglobe_atlasapi` and `.. autosummary::` directives, instructing Sphinx to automatically generate documentation from the module's docstrings.
    - New script (e.g., `docs/fetch_repos.py`): Implements `subprocess` calls to `git clone` or `git pull` specific Brainglobe repositories into a designated `_external_repos` directory for local processing by Sphinx.
    - `requirements.txt` (or a similar `docs/requirements.txt`): Updated to include `sphinx`, `sphinx-rtd-theme`, `numpydoc` (or `sphinx-napoleon`), `sphinx-autodoc-typehints`, and other required Python packages for the Sphinx build environment.
- **Technologies Used**: Python, Sphinx, `sphinx.ext.autodoc` (for docstring parsing), `sphinx.ext.napoleon` (for parsing NumPy/Google style docstrings), `sphinx.ext.intersphinx` (for linking to external project documentation), and `git` (for fetching external repositories).
- **Implementation Approach**: The core approach involves programmatically fetching external Python packages, then dynamically configuring Sphinx's `sys.path` to allow `autodoc` to import and inspect their modules. `autodoc` directives are then used in `.rst` files to define which modules, classes, and functions have their docstrings converted into documentation.
- **Architectural Changes**: This PR introduces a significant architectural shift in how documentation is managed, moving from manual static pages towards a more dynamic, automated, and federated approach. It sets up the infrastructure for creating a "documentation monorepo" that aggregates API references from multiple underlying code repositories. This reduces coupling between individual libraries and the documentation website while ensuring up-to-date content.
