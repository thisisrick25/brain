# Contribution Summary

## What was done

- The primary action involved the removal of all codebase references and implementations related to an internal transformation process that previously converted atlas data into a specific "BrainGlobe orientation."
- This change specifically targets and eliminates the logic responsible for reorienting atlases, ensuring that the `brainglobe-atlasapi` now exclusively expects and operates on atlases provided directly in the anterior-superior-right (asr) orientation.
- The modification simplifies the atlas loading and processing pipeline by removing the need for runtime coordinate system adjustments within the API.
- This contribution directly addresses and closes issue [#547](https://github.com/brainglobe/brainglobe-atlasapi/issues/547), which likely pointed to complexities or inconsistencies arising from the previous implicit transformation approach.

## Impact

- **User Impact**: Users are now explicitly required to ensure any custom atlases they provide or interact with are already in the `asr` orientation. While this clarifies expectations for new atlas contributions, it implies that atlases not originally in `asr` will no longer be implicitly transformed by the API. For existing, officially supported atlases within the API, which are presumed to already adhere to the `asr` standard, there is no negative impact on their functionality.
- **System Impact**: The internal architecture of the `brainglobe-atlasapi` is significantly simplified. By removing complex and potentially error-prone transformation logic, the codebase becomes more maintainable, reducing potential sources of bugs related to coordinate system misalignments or incorrect reorientations.
- **Performance**: A minor performance improvement is expected due to the elimination of computational overhead previously incurred during coordinate system transformations upon atlas loading.
- **Functionality**: The change fosters greater consistency and predictability in how atlas orientations are handled, ensuring a uniform coordinate system (`asr`) across all operations within the API, which streamlines internal data handling.

## Technical details

- The core technical change involved identifying and deprecating or removing functions, methods, and configurations specifically responsible for `BrainGlobe` specific orientation transformations. This included any code that performed axis swaps, inversions, or affine matrix adjustments to align an atlas to the previous internal "BrainGlobe orientation" standard.
- These modifications typically reside in modules handling atlas dataset loading (e.g., `brainglobe_atlasapi.atlases.base`), `nibabel` volume processing, and potentially utility functions related to spatial transformations and metadata interpretation.
- The implementation approach fundamentally shifts the responsibility of orientation consistency from the API's internal logic to the data source (i.e., the user-provided atlas). The API now implicitly assumes the `asr` orientation for all input and internal processing, rather than actively enforcing it through transformation.
- This design decision aligns the API with a single, clear spatial convention, streamlining future development, reducing the cognitive load for developers, and simplifying the overall data pipeline.
